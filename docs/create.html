THE CREATOR PATH / LOCAL & OPEN

Make it fit your idea.

Use your AI coding assistant to change understandable dimensions, not to guess whether a mesh is printable. Everything runs locally; there is no hosted AI generator.

Get the source

Install Python 3.11 or newer and clone the repository. The core model tools need no third-party packages. Run commands from the repository root. A model's source ZIP also contains the files needed for the core CLI; unzip before running it.

git clone https://github.com/Prashanth261993/OpenPrintLab.git
cd OpenPrintLab
python -m tools.cli list
python -m tools.cli parameters pocket-tray
python -m tools.cli check pocket-tray --set length=120
python -m tools.cli build pocket-tray --set length=120

The last command writes build/pocket-tray.stl and a JSON report. Repeating it replaces those files; use --output build/my-variant to keep a separate variant. A check failure exits nonzero and explains why. Open the STL in Bambu Studio and follow the beginner workflow; a software report cannot replace slicing.

What can be customized?

models/catalog.json contains the default dimensions and descriptions. models/recipes.py defines three original parametric designs: trays, open-channel rests and staircases. Dimensions are millimeters; counts are integers. The CLI exposes the exact supported limits, rejects unknown keys and validates relationships such as remaining compartment width.

These are simple box-union solids, not a general CAD kernel. They have square corners, not rounded fillets. Generated OpenSCAD files are inspection snapshots of the same boxes; editing one does not update the Python source or report. For a new curved or organic object, choose an appropriate CAD tool and add a real export/validation pipeline before claiming support.

Two creation paths, different promises

Precise functional CAD is the shipped path: the original four models remain dependency-free. The separately approved optional CadQuery template lab adds rounded organizers, multi-pen rests and lightweight paper-card stands. Give instructions to your own tool-capable assistant, which uses the shared CLI/MCP to create a fresh variant and actual geometry preview. The local walkthrough includes exact commands and prompts. This is not a hosted chatbot or a wholesale catalog migration.

Decorative AI meshes are a planned, optional path: a visual prompt is not dimensional intent. An attractive mesh still needs size, thickness, topology, rights and human slicer checks. The reuse plan evaluates Meshy's official MCP or skill instead of a duplicate wrapper, with explicit account/privacy/output-license review and a credit cap. FreeCAD and Blender community bridges, Zoo/KCL and Tripo are deferred candidates, not installed integrations. No provider API has been connected or called.

Read the staged reuse plan before approving an experiment. The local no-key tools keep working regardless of those decisions.

Custom decorative prototypes, not automatic structural approval

For requests involving joints, glazing, loads or mounting, read the canonical structural-prototype guide. Eligible non-safety-critical decorative designs can be explored using reviewed task-specific CAD. Frames and general assemblies are not built-in templates: identify custom engineering and unsupported checks rather than changing the catalog to claim support.

The guide defines hazard escalation and hard exclusions, complete load paths and mass budgets, geometry and coupon deliverables, reversible service access and staged physical evidence. Unknown installation conditions remain unresolved inputs, not a ban on all modeling. Keep the explicit state Prototype - not validated for hanging/load use. Neither a manifold model nor one successful print or short test establishes suitability.

Keep the passport with your model

Each JSON report is also a model passport: model version, effective dimensions and parameters, variant ID, editable-source hashes, exact STL SHA-256, CC BY 4.0 design license and a separately labeled suggested P2S recipe. The evidence scope binds that exact version, variant and STL hash. The recipe is not a record of actual settings used.

Every export reruns geometry checks. A dimension or source change produces a new variant identity; slicer and physical records remain not_performed with no invented actual settings. A model version change needs maintainer review. Never copy a successful print report to another variant.

Optional local MCP integration

For an MCP-capable assistant, install the official SDK in a virtual environment using the optional dependency. Use an editable install from this trusted clone; exports are kept in the clone's build/mcp directory.

python -m venv .venv
# Windows:
.\.venv\Scripts\python.exe -m pip install -e ".[mcp]"
# macOS/Linux:
.venv/bin/python -m pip install -e ".[mcp]"

Add a local stdio server in your client's MCP settings. For clients using an mcpServers JSON object, the Windows example below works after replacing both absolute paths. Other clients use different configuration wrappers: preserve the command and arguments, and follow your client's documentation.

{
  "mcpServers": {
    "openprintlab": {
      "command": "C:\\path\\OpenPrintLab\\.venv\\Scripts\\python.exe",
      "args": ["-m", "tools.mcp_server"],
      "cwd": "C:\\path\\OpenPrintLab"
    }
  }
}

The four tools are list_models, describe_model, check_model, and export_model. Ask the assistant to describe a model, check proposed parameters, then export after your approval. Export replaces the previous MCP export for that model. It only accepts known model IDs and numeric parameters; there are no shell, arbitrary-path, network or printer-control tools. Your MCP client controls tool approval. Run only trusted source code.

Those are the original model tools. The template lab adds list_templates, describe_template, create_variant and variant_guidance. For optional CAD generation, configure the separate CAD interpreter with ["-m", "tools.mcp_server", "--cadquery"]; see the complete setup and prompts. New variants refuse overwrites and return real preview/download paths.

Contribute a model, not an unsupported promise

State the intended use and exclusions, dimensions, limits, material, orientation and expected clearance. Add original design source and catalog metadata, tests for invalid dimensions and analytical geometry, and regenerate all exports with python -m tools.release. Run python -m unittest discover -s tests -v and python -m tools.release --check. Then build the site with python -m tools.site.

Do not silently promote validation levels. A slicer review needs the STL hash, application version, exact printer/nozzle/plate/material/process selections, warnings and preview observations. A physical test additionally needs real photos, date and outcomes. New dimensions invalidate the old evidence. Record this in a review or issue until the catalog supports evidence-backed promotion.

Use the print-result form for successes, partial successes, failures or a trial stopped before printing. Include the passport identifiers, actual settings and relevant photos/screenshots, or explain why evidence is unavailable. Issues are public: remove private details, credentials and serial numbers. Reports do not automatically promote model status.
